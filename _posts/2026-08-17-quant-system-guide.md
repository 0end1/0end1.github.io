> 结合对数据源、回测框架、执行通道、系统架构四方面的调研，为「个人开发者 + Python 背景 + A股/期货半自动量化」整理的一份 2026 年选型与实施指南。

---

## 为什么写这篇

2026 年的个人量化生态和几年前相比变化很大：券商量化终端 QMT/miniQMT 的权限门槛大幅下降（从传统 50 万降到数万元，甚至一度出现「2 万开通」的活动），程序化交易新规落地后合规要求更明确，TqSdk 等免费期货工具已经成熟，开源生态（Vn.py、Qlib、NautilusTrader）持续演进。

对个人来说，用 Python 搭一套覆盖「数据 → 研究 → 信号 → 执行 → 风控」的半自动系统，技术上完全可行。关键是在每一层选对工具、控制成本、守住风控底线。

本文面向的场景是：**A股 + 国内期货（股票/可转债/商品期货）、半自动形态（策略出信号 → 人工确认 → 下单）**。如果你是全自动或纯研究向，部分结论需要调整。

## 一、数据源选型：先解决「数据从哪来」

行情与基本面数据是量化系统的地基。下表是 2026 年个人可用的主要数据源对比：

| 数据源 | 覆盖范围 | 接口/语言 | 成本 | 稳定性 | 适合场景 |
|---|---|---|---|---|---|
| Tushare Pro | A股、基金、期货、债券、指数；日线/分钟线/财务/资金流 | Python API，Token 鉴权 | 免费注册；积分制（120 元/200 积分，2000 积分解锁大部分日线+财务，分钟线需更高积分） | 高，数据规范 | 主力数据源，A股财务与日线首选 |
| AkShare | A股、期货、可转债、宏观、另类数据；3000+ 接口 | Python API，完全免费 | 免费 | 中，接口源自东财/新浪等，偶有变动 | 免费补充源、可转债、快讯、特殊数据 |
| Baostock | A股日线/财务/指数 | Python API | 免费 | 高但更新慢，无分钟线/tick | 历史日线备选 |
| 聚宽/米筐云端 | A股全谱 | 网页/notebook | 个人免费版 | 高 | 云端研究、快速回测、策略托管 |
| QMT/miniQMT 数据 | A股/可转债/ETF/期货行情（含分钟线、部分 tick） | xtquant Python | 随开通权限附带 | 高 | 已开通 QMT 时可直接白嫖行情 |
| Wind/iFinD | 机构级全市场数据 | Python/R 插件 | 贵（iFinD 个人年费数千，Wind 更高） | 极高 | 预算充足时增强，个人通常不必要 |
| 天勤 TqSdk | 期货/期权全品种，历史+实时 | Python，pip 安装 | 免费（登录即可） | 高 | 期货行情+回测+实盘，个人期货首选 |
| 集思录/AkShare 可转债 | 可转债价格/条款/溢价率 | 网页/Python | 免费 | 中 | 可转债策略数据 |

几个社区里反复被提到的经验：

**一定要做统一数据层。** 2026 年有很多文章反思「纯依赖 AkShare/Tushare 直接调接口」的做法——接口变动频繁、历史数据补齐慢、分钟线获取受限。主流做法是在数据源之上加一层本地库（SQLite/DuckDB/Parquet），策略和回测只读本地库，换数据源不伤策略。

**分钟线数据量要提前评估。** A股全市场一分钟线约合 4000 只 × 240 分钟 ≈ 96 万条/天，一年约 2.3 亿条，直接每次联网拉取不可行，必须本地落库并做增量更新。

**可转债没有独立的官方行情源。** 社区主流是 AkShare/Tushare 接口 + 集思录网页抓取双保险。

推荐组合：**Tushare Pro（日线+财务，主力）+ AkShare（可转债/快讯/补充）+ 天勤 TqSdk（期货）+ 本地 DuckDB/Parquet 统一数据层**。若已开通 QMT，其自带行情可以作为分钟线主力源。

## 二、回测与研究框架：选对再投入

| 框架 | 适用市场 | 回测能力 | 实盘/信号衔接 | 学习曲线 | 维护状态（2025-2026） |
|---|---|---|---|---|---|
| Vn.py（VeighNa） | A股+期货全支持，CTP 原生 | 事件驱动，可回测+仿真+实盘 | 强，含 CTP/TqSdk/券商通道 | 中高 | 活跃，3.x 重构后社区活跃 |
| Backtrader | 通用（需自接数据） | 成熟，指标丰富，文档全 | 弱，需自行接实盘 | 低-中 | 基本停更（原维护者多年未更新） |
| Qlib（微软） | A股内置数据 | 偏因子/AI 研究，支持滚动训练 | 弱，研究导向 | 高 | 活跃但迭代放缓 |
| 聚宽/米筐云端回测 | A股 | 成熟、免费额度 | 可仿真盘/实盘 | 低 | 稳定商用 |
| VectorBT | 通用 | 基于 NumPy 向量化，超快，适合参数扫描 | 弱 | 中 | 活跃 |
| NautilusTrader | 期货/外汇/加密 | Rust 内核，毫秒级，事件驱动 | 强 | 高 | 活跃，2026 年关注度高 |
| Zipline | 美股为主 | 成熟 | 弱 | 中 | A股适配差，不推荐 |
| 自建轻量回测 | 自定 | pandas/NumPy 自写，灵活可控 | 自定义 | 中 | — |

几点判断：

- **Backtrader 资料多、上手快，但维护基本停滞**，并行性能弱，长期看不是最优投入。
- **Vn.py 是 A股+期货场景最完整的开源框架**，回测与实盘通道（CTP、券商）统一，学习成本换来的是全链路能力。
- **Qlib 只在做多因子/AI 选股研究时值得引入**，且常需与 Alphalens/Pyfolio 配合做因子检验。
- **聚宽等云端平台适合策略原型快速验证**，几分钟跑通思路；但数据取不出平台、受平台限制。
- 2026 年的一个趋势是「**轻量自建回测 + VectorBT 扫参**」。对逻辑清晰的趋势/轮动策略，自建 200-300 行回测引擎配合本地数据库，可控性最好，也避免了黑箱框架的坑（前视偏差、复权错误、停牌处理等）。

推荐路线：**策略研究以「聚宽/米筐云端 + 本地轻量回测」起步，重策略（如多因子）引入 Qlib，最终落地实盘时用 Vn.py 或自建信号引擎接 miniQMT/TqSdk**。

## 三、半自动执行：信号怎么推、单怎么下

半自动 = 策略出信号 → 推送通知 → 人工确认 →（人工或程序）下单。这是本方案的核心差异化环节。

### A股执行通道

| 方案 | 权限门槛（2026） | 支持品种 | Python 能力 | 稳定性 | 备注 |
|---|---|---|---|---|---|
| miniQMT（迅投 xtquant） | 券商开户+资金门槛，2026 年低至 2-5 万（华鑫/国金等，政策变化快，部分地区低门槛活动已下架） | 股票/可转债/ETF/基金/期权等 | 官方 Python API，可无界面运行 | 高 | 当前个人 A股 量化事实标准 |
| QMT 完整版 | 同 miniQMT，一般资金门槛更高 | 同上 | 图形界面+Python | 高 | 界面化，适合人工+程序混合 |
| PTrade（恒生） | 券商开通，门槛与 QMT 相当 | 股票/可转债 | 内置 Python 策略运行 | 高 | 云端托管式，策略留在券商端 |
| Easytrader 等模拟点击 | 无（普通账户） | 股票 | 模拟客户端点击 | 低 | 2025-2026 已基本不可靠，安全与合规风险高，不建议 |
| 券商量化专区/条件单 | 无 | 股票/可转债 | 不支持编程 | 高 | 只能做简单条件单，非真量化 |

一个必须提醒的事：**miniQMT 权限政策在 2026 年上半年剧烈波动**。3 月曾出现「2 万开通 miniQMT」（华鑫）与「5 万开通 QMT+miniQMT+PTrade」的推广，但随后又传出低门槛活动下架、重回 50 万门槛的消息。开通门槛是动态的，务必以开户券商当下的最新政策为准，且建议选头部券商以保长期稳定。miniQMT 的优势在于本地运行 Python（xtquant），行情 + 下单一体化，支持可转债，是个人半自动系统最顺滑的执行通道。

### 期货执行通道

| 方案 | 门槛 | 能力 | 稳定性 | 备注 |
|---|---|---|---|---|
| 天勤 TqSdk | 免费，注册登录即可，SimNow 仿真免费 | 行情+回测+实盘交易一体化，Python | 高 | 个人期货量化的主流免费方案 |
| CTP 直连（vn.py CTP 模块） | 需期货公司开通 CTP 实盘权限（一般有资金门槛） | 毫秒级、全功能 | 高 | 追求速度与自主控制时选择 |
| 期货公司自带条件单/跟单 | 低 | 简单条件 | 高 | 非真量化 |

天勤 TqSdk 在 2026 年社区里基本是「纯免费个人期货量化」的标准答案（SimNow 仿真 + 实盘切换一行代码），从行情到信号到仿真下单闭环完整，半自动场景优先推荐。

### 信号通知渠道

| 渠道 | 实时性 | 成本 | 可靠性 | 备注 |
|---|---|---|---|---|
| 企业微信机器人 | 秒级 | 免费 | 高 | 支持 Markdown/图片，个人可自建群机器人，最推荐 |
| 钉钉机器人 | 秒级 | 免费 | 高 | 同上，国内稳定 |
| Server酱/PushPlus | 秒级 | 免费额度有限，付费低 | 高 | 简单，微信端接收 |
| Telegram Bot | 秒级 | 免费 | 高 | 需网络代理，国内不稳 |
| 邮件 | 秒级-分钟级 | 免费 | 高 | 延迟偏大，适合日报 |

推荐链路：**策略定时任务（APScheduler）→ 计算信号 → 企业微信/钉钉机器人推送（含标的、方向、价格、建议仓位、K线截图）→ 用户在券商 App 或 miniQMT 界面人工确认下单 → 程序记录成交并回写**。

半自动形态下「程序只负责提醒、人负责最终下单」，既能享受量化纪律，又规避了全自动的程序化交易报备复杂度与断网/断行情风险。若未来想升级为全自动，miniQMT/TqSdk 均已具备程序下单能力，只需加一道二次确认。

## 四、系统架构与基础设施

推荐五层架构（与 2026 年社区主流实践一致）：

- **数据层**：Tushare/AkShare/TqSdk 定时拉取，写入本地 DuckDB/Parquet（日线、财务、可转债、期货全部落库），分钟线按需增量。日线/财务用 DuckDB 或 SQLite 足够；分钟线累计到亿级后 DuckDB 仍能单机扛住（列式+压缩），ClickHouse 仅在超大规模时引入；MySQL/PostgreSQL 适合多端共享或需要事务的场景，个人本地系统可用可不用。Redis 可选作实时行情缓冲。
- **研究层**：Notebook + pandas/NumPy/TA-Lib/statsmodels；因子检验用 Alphalens/Pyfolio；多因子/AI 用 Qlib。
- **策略层**：策略代码统一接口（接收 DataFrame，输出信号 DataFrame），与数据源解耦。
- **信号层**：APScheduler（个人最合适，比 Airflow 轻得多，Cron 亦可）按周期跑策略，产出信号并推送企业微信/钉钉，同时写入本地「信号/成交」记录表。
- **执行层**：A股走 miniQMT（xtquant）或人工确认后由程序挂单；期货走 TqSdk 或 vn.py CTP；人工确认通过消息按钮/App 完成。
- **监控层**：进程健康检查 + 行情断流检测（行情源连续 N 秒无推送即告警）、任务失败告警、每日信号汇总日报；告警渠道复用企业微信/钉钉；可视化 Grafana 个人场景常被评价为过重，日志+告警足够。

**服务器选型**：本地 Mac/PC 跑研究没问题；生产定时任务建议国内云服务器（阿里云/腾讯云轻量应用服务器，2 核 4G 约 100-200 元/月，4 核 8G 约 300-500 元/月，2026 年常态价），国内节点行情接入延迟低、稳定性好；预算敏感时 2 核 4G 足够跑信号与推送。

**风控必做清单**（这是半自动系统最容易偷懒也最致命的部分）：

- 单票/单品种仓位上限（如单票不超过总资金 20%、期货按保证金+波动率控制）
- 固定比例或 ATR 止损
- 组合最大回撤阈值（触发即降杠杆或停止开仓）
- 单日最大亏损熔断
- 期货换月损耗处理与保证金盯市（CTA 策略回撤主要来源之一：换月损耗、剧烈波动、极端行情）
- 可转债下修/强赎条款跟踪

风控逻辑必须独立于策略代码（独立模块或独立进程），并写入系统级熔断：**行情异常/断连时禁止开新仓**。

## 五、三套推荐方案（按投入与目标选择）

**方案 A（低成本快速起步，适合先验证想法）**：Tushare 免费积分 + AkShare + 本地 SQLite/DuckDB；聚宽云端做回测；Backtrader 或自建轻量回测；信号用企业微信机器人推送，人工在券商 App 下单；期货暂用 TqSdk 仿真。总成本近 0，核心目的是验证策略与流程跑通。

**方案 B（标准半自动，主推）**：Tushare 2000-5000 积分（约 120-600 元）+ AkShare + TqSdk；本地 DuckDB 统一数据层；回测 Vn.py + Qlib（因子部分）；开通 miniQMT（2-5 万资金门槛，具体以券商当期政策为准）作 A股执行通道、TqSdk 作期货通道；APScheduler + 企业微信/钉钉推送 + 人工确认下单；2 核 4G 云服务器（约 100-200 元/月）+ 风控模块。总成本一年千元级，覆盖股票/可转债/期货半自动全链路。

**方案 C（进阶，追求更多自控与速度）**：方案 B 基础上，执行层改用 vn.py CTP 直连期货、miniQMT 全自动（含二次确认），数据层引入 ClickHouse 存分钟线，研究层引入 Qlib 多因子与机器学习，监控上 Grafana + Prometheus，服务器升 4 核 8G。适合策略验证成熟、想提高执行质量与吞吐的阶段。

## 六、实施路线图

- **第一阶段（1-2 周）**：搭数据层——注册 Tushare 拿积分、装 AkShare/TqSdk，建 DuckDB 本地库与增量更新脚本，把日线/财务/可转债/期货数据落库。
- **第二阶段（2-4 周）**：写第一个策略（如均线趋势/双低可转债），在聚宽或本地回测验证，跑通「策略→信号→推送」链路，接入企业微信机器人。
- **第三阶段（4-8 周）**：开通 miniQMT/TqSdk 实盘权限，做仿真盘试运行 2-4 周，同时补全风控模块（仓位/止损/回撤/熔断）。
- **第四阶段**：小资金实盘半自动运行，人工确认下单，持续记录信号与实际成交差异（滑点、未成交），迭代策略。

## 结论

对「有 Python 基础的个人做 A股+国内期货半自动量化」，2026 年的可行组合已经非常清晰：数据用 Tushare Pro + AkShare + TqSdk，本地落 DuckDB/Parquet；研究回测用云端平台起步、Vn.py/Qlib 深入；A股执行走 miniQMT（门槛低但政策波动大，需实时核实券商政策），期货执行走免费的 TqSdk；信号推送用企业微信/钉钉机器人实现人工确认；基础设施上国内轻量云服务器 + APScheduler + 独立风控模块即可。按「数据层 → 策略 → 信号推送 → 仿真 → 小资金实盘」的顺序推进，总投入可控制在一年千元级。

系统形态保持「程序提醒、人工确认」，在合规与可靠性上是最稳妥的半自动路径；若后续要全自动，现有通道（miniQMT/TqSdk/CTP）已具备升级能力。

## 局限与说明

miniQMT/QMT 的券商开通门槛在 2026 年处于快速变动期（既有 2-5 万的低门槛推广，也有活动下架重回 50 万的传闻），本文给出的是区间与趋势判断，落地时必须向目标券商核实当期政策；Tushare 积分对应的接口权限随平台政策调整，以官网为准；云服务器价格区间为 2026 年常见促销价，实际以云厂商报价为准。各开源框架维护状态可能随时间变化，投入学习前建议核对 GitHub 最近提交。
